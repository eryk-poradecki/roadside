# Photos live on disk, are served by an endpoint, and are shown to the model when it can see

> **Amended by [ADR 0005](0005-rest-conventions-and-endpoints.md):** all paths live under `/api/v1` (e.g. `GET /api/v1/photos/{id}`). The sixth photo is refused with 409 `photo_limit`, not 422.

An incident has up to five photos, each added or removed on its own. The bytes are files on disk in `UPLOAD_DIR` (a named docker volume) under server-generated UUID names, and each one has a row in `incident_photos` (`incident_id` FK with `ON DELETE CASCADE`, `stored_name`, `content_type`, `size_bytes`, `width`, `height`, `created_at`). Photos are served only through `GET /api/photos/{id}`, never a static mount, so the database stays the source of truth: a deleted row's file is unreachable at once, a missing photo is a clean 404, and there is one place to add cache headers or auth later. When the provider supports images, the model sees the photos, because a picture of a pothole or a shredded tyre tells it more than a problem type and a note.

## Considered Options

- **BLOB column in SQLite**: one-file backup and atomic deletes. Rejected: bloats the database, pushes image bytes through the ORM, and is an unusual choice for a few hundred KB per file.
- **`StaticFiles` mount on the upload folder**: less code. Rejected: it serves whatever is in the folder regardless of the database, so it is the less secure design.
- **One multipart create carrying the incident and its files**, or **upload first, attach by id**: rejected. The first makes the create endpoint non-JSON. The second leaves orphan files when the create never happens. Instead the incident is created with JSON (ADR 0001) and photos go to `POST /api/incidents/{id}/photos`, one file per request. The same endpoint adds photos later from incident detail. `DELETE /api/photos/{id}` removes one.
- **Store only (no vision)** or **always vision**: rejected. Vision is behind a provider capability flag (`LLM_VISION`), so text-only models keep working.

## Consequences

- **Guardrails, client and server.** The client downscales to a 1600 px long edge and re-encodes as JPEG (~0.8) before upload, to suit a weak roadside connection. The server is the real gate, because API clients bypass the frontend. It caps files at 10 MB (413), accepts JPEG, PNG and WebP only, and checks the type by decoding, not by trusting `Content-Type`. It allows at most 5 photos per incident.
- **Server pipeline order is fixed:** decode with Pillow → `ImageOps.exif_transpose` → limit the long edge to 2048 px → re-encode without metadata → write the file → commit the row. Orientation must be applied before EXIF is dropped, or portrait phone photos come out sideways. Stripping EXIF also drops the photo's GPS tag: the incident already stores location explicitly and the photo should not leak it.
- **File and row stay consistent by ordering, not transactions.** Write the file, then commit the row, and remove the file if the commit fails. On delete, remove the row, then the file, and ignore a missing file. An FK cascade removes rows only, so deleting an incident deletes its files in the service.
- **AI timing.** At "Get help now" the incident is created, photos upload in parallel while the safety checklist shows, and the AI request starts once every upload has succeeded or failed. A failed upload never blocks the AI.
- **What the model gets.** Photos in upload order, capped by `LLM_MAX_IMAGES` (default 3; free tiers allow 2–3 per request), downscaled to 1024 px for the request only and sent as base64 data URLs. When the cap or a text-only provider hides photos, the prompt says how many were not seen. The AI answer must state whether it saw photos and what it observed in them, so the UI can label it (shape decided in the AI design).
- **Photos added after the answer do not change it.** The AI answer stays write-once (ADR 0001). Later photos document the incident, e.g. for the damage report. A retry after a failed answer uses the photos present at that time.
- **Privacy.** Hosted free tiers (Gemini) may use inputs to improve their products, and photos can show plates, faces or a street. Vision is allowed on hosted providers. The README states this, and the photo sheet shows "Photos are sent to the AI provider" whenever vision is on.
- **Demo mode accepts no uploads.** The public deploy must not store strangers' files. The server rejects file uploads with 403 in demo mode (the hidden button is not the guard). The same endpoint accepts `{"sample_id": ...}` for a known bundled sample photo, which is copied into `UPLOAD_DIR` as an ordinary photo, so the limit, deletion and vision behave the same. Sample photos are public domain, CC0 or CC-BY, or the author's own with plates blurred, each credited in `docs/ATTRIBUTION.md`.
- **No thumbnails in the MVP.** Stored files are small after downscaling, and lists use `loading="lazy"`. A second stored size is a follow-up if time allows.
